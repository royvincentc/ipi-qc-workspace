\# IPI Frontend Design Protocol



For any UI/UX change:



1\. Inspect the existing implementation before making changes.



2\. Use installed design skills when applicable:

&#x20;  - Emil-inspired interface design guidance

&#x20;  - Impeccable

&#x20;  - Taste



3\. Avoid generic AI-generated SaaS aesthetics.



4\. Prefer:

&#x20;  - strong information hierarchy

&#x20;  - restrained borders

&#x20;  - deliberate whitespace

&#x20;  - high information density without visual crowding

&#x20;  - minimal nesting of cards

&#x20;  - excellent typography

&#x20;  - subtle, physically believable motion

&#x20;  - responsive behavior

&#x20;  - keyboard accessibility



5\. Do not introduce a new component if an existing project component can

&#x20;  be extended cleanly.



6\. After implementing visual changes:

&#x20;  - start the development server

&#x20;  - inspect the result using Playwright

&#x20;  - interact with affected UI

&#x20;  - test desktop and mobile widths

&#x20;  - capture screenshots when useful

&#x20;  - inspect for overflow and broken states



7\. Run an Impeccable critique/audit after substantial frontend changes.



8\. Fix significant findings before declaring the task complete.



9\. Code compilation alone is not evidence of successful UI implementation.



10\. The rendered application is the source of truth.
